# Bastion LNURL API

## Architecture and response semantics

The `/v1/lnurl` router is a thin adapter over the existing LNURL-auth, principal,
session bridge, payment request/callback/verify, Payment Proof, entitlement, and
withdraw services. Bastion-side POST operations use the normal API envelope.
Wallet callback and verification GET operations return raw LNURL protocol JSON so
wallets are not broken by a Bastion wrapper.

LNURL-auth proves control of a domain-specific Lightning linking key. It does not
prove ownership of a Bitcoin treasury address. For on-chain ownership proof, use
the configured Bitcoin Wallet Proof path such as BIP-322. A completed callback must
still pass Lightning Principal, Device Binding, Subscription Entitlement, PoP
Session, Policy Engine, Revocation Registry, and Audit Chain controls.

## Routes

* `POST /v1/lnurl/auth/challenges` creates a server-generated, 32-byte, short-lived,
  action/domain/device/policy-bound k1 challenge.
* `GET /v1/lnurl/auth/callback` verifies the wallet's secp256k1 proof and atomically
  consumes k1. It never issues an API session itself.
* `POST /v1/lnurl/auth/sessions` converts one completed attempt into a Device-bound
  PoP Session after entitlement, revocation, risk, and policy checks.
* `POST /v1/lnurl/auth/step-up` binds fresh LNURL `action=auth` to a Bastion Human
  Intent; it is short-lived and cannot authorize another action.
* `POST /v1/lnurl/pay/subscriptions` creates a canonical subscription pay request.
* `GET /v1/lnurl/pay/callback/{payment_id}` asks the configured provider for an
  invoice. LNURL-pay invoice creation does not equal payment settlement.
* `GET /v1/lnurl/pay/verify/{payment_id}` verifies trusted settlement state. Only
  settled state may create one Payment Proof and one idempotent entitlement.
* `POST /v1/lnurl/withdraw/requests` creates a policy-approved payout capability.
* `GET /v1/lnurl/withdraw/callback/{withdraw_id}` validates k1 and the supplied
  invoice before the payout service performs an atomic redemption transition.
* `GET /.well-known/lnurlp/{name}` remains the existing product/merchant Lightning
  Address discovery route. Lightning Address is payment routing, not identity.

## Security boundaries

k1 values are generated by the service, expire quickly, and are consumed once in
shared persistent state. Missing records are never recreated. The auth domain and
callback base URL come from trusted configuration, never `Host` or forwarded-host
input. Clearnet callbacks require HTTPS; Onion behavior requires an explicit gate.

Public callback/discovery GET responses receive `Access-Control-Allow-Origin: *`
without credentials. Authenticated Bastion POST operations do not receive route-
level wildcard CORS, and global credentialed wildcard CORS is not enabled.

Comments and payerData are untrusted metadata. They cannot select plans, principals,
roles, scopes, recovery paths, refunds, or entitlement state. `payerData.email` is
optional and is never identity. Invoice issuance never activates access, and caller-
supplied settlement state is ignored.

LNURL-withdraw is a payout capability and must be protected by Policy Engine before
issuance. Final payout also rechecks request state, revocation, invoice amount and
network, risk, and policy. Atomic status transitions and idempotent payout tasks
prevent replay.

Bastion never asks for Bitcoin wallet seeds, Lightning wallet seeds, mnemonics,
xprvs, channel backup secrets, node macaroons, or private keys in these user-auth
flows. External Lightning providers are deployment dependencies; merely exposing
routes does not make an unconfigured deployment production-ready.
