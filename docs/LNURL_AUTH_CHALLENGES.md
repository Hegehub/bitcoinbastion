# LNURL-auth Challenges

This document describes Bastion's LNURL-auth challenge creation boundary. It creates a scannable LNURL-auth challenge only; callback signature verification, Lightning Principal creation, Proof-of-Possession session issuance, and entitlement issuance are handled by later services.

## Flow

1. A trusted caller requests an LNURL-auth challenge with a standard LNURL action (`register`, `login`, `link`, or `auth`).
2. Bastion maps that external action to an internal policy intent such as `wallet_principal_authenticate` or `wallet_sensitive_action_step_up`.
3. The LNURL k1 registry creates a single-use 32-byte challenge and stores only protected lookup material.
4. The challenge service builds a callback URL from trusted configuration, validates it with the central LNURL URL safety policy, and encodes it with the LNURL Bech32 encoder.
5. The public response is suitable for QR rendering and includes a user warning that the Lightning wallet signature is not a payment or withdrawal authorization.

## k1 Rules

- k1 is generated by the k1 registry from 32 cryptographically random bytes.
- The callback carries k1 as 64 lowercase hexadecimal characters because the wallet must sign it.
- Persistence stores protected lookup hashes and fingerprints, not raw k1.
- Challenges are short-lived and single-use by registry design.
- Used, cancelled, revoked, or expired challenges must not be treated as active.

## Stable Auth Domain

LNURL-auth identity is domain-specific. The challenge service builds callbacks from trusted configuration (`LNURL_AUTH_PUBLIC_BASE_URL` and `LNURL_AUTH_CALLBACK_PATH`) and validates that the public base URL matches the configured stable auth domain. It never derives the auth domain from request headers.

## Action and Policy Binding

The callback URL contains only `k1` and the standard LNURL `action`. Server-side records bind the challenge to:

- external LNURL action;
- internal Bastion action;
- auth domain and origin;
- policy hash and internal intent hash;
- risk level;
- optional device key fingerprint;
- optional principal hint hash;
- requested scopes.

The external `auth` action is not an unrestricted approval. Sensitive details remain server-side and are validated again by later callback, principal, session, entitlement, revocation, and Policy Engine layers.

## Logging, Audit, and Redaction

Audit events include opaque challenge IDs, k1 fingerprints, action names, domain, policy hash, risk level, and timestamps. They must not include raw k1, raw LNURL strings, raw callback URLs containing k1, wallet linking keys, signatures, session tokens, or recovery material.

## Not Authentication Success

Challenge creation is not authentication success. It does not verify a Lightning wallet signature, create a Lightning Principal, issue a PoP session, issue an entitlement, or authorize protected API access.
